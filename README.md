# 基层法院诉前调解排期与协议履行平台

面向基层法院的诉前调解一体化平台：当事人在线提交申请 → 立案窗口分流 → 调解中心按案由/专长/双方时间/外地当事人智能排期 → 调解员线上线下调解并记录 → 协议人脸核验与线上签署 → 分期履行跟踪与逾期预警 → 回访、司法确认或转立案。**所有角色围绕同一案件推进，全部过程统一进入案件时间线，多次改期、失联、部分履行等情形可一键汇编成连续材料卷提交法官，避免在调解与立案窗口间反复补材料。**

## 技术栈

- 后端：Java 17、Spring Boot 3.2、Spring Data JPA
- 数据库：**默认 H2 内存库（MySQL 兼容模式），免安装零配置**；同时提供 MySQL 连接配置
- 前端：Vue 3 + Vite + Element Plus + ECharts
- 鉴权：登录令牌（内存 Token 存储，Bearer 头）

## 本地启动

### 方式一：单 jar 启动（推荐，已构建好前端产物）

前置：JDK 17、Maven 3.8+。

```bash
cd backend
mvn package -DskipTests
java -jar target/mediation-platform.jar
```

浏览器打开 <http://localhost:8080/> 即可（前后端同源，无需额外启动前端）。
H2 控制台（可选）：<http://localhost:8080/h2-console>，JDBC URL `jdbc:h2:mem:mediation`，用户名 `sa`，密码空。

### 方式二：前后端分离开发（热更新）

```bash
# 终端1：后端
cd backend && mvn spring-boot:run

# 终端2：前端（5173 端口，/api 自动代理到 8080）
cd frontend && npm install --cache /tmp/npm-cache && npm run dev
```

打开 <http://localhost:5173/>。

### 方式三：Docker / Compose 一键启动（无需本机 JDK/Node）

前置：Docker（含 Compose 插件）。镜像内多阶段构建前端+后端，产出单 jar 运行。

```bash
# 默认 H2 内存库
docker compose up -d --build
# 打开 http://localhost:8080/ ；查看日志 docker compose logs -f mediation

# 可选 MySQL 版本（自动拉起 mysql:8 并以 mysql profile 启动应用）
docker compose -f docker-compose.yml -f docker-compose.mysql.yml up -d --build
```

> 说明：当前隔离验证环境无 Docker 守护进程，上述镜像未在本机实际构建；Dockerfile 采用 Node 构建前端 → Maven 构建后端 → JRE 运行的标准多阶段构建，等价的前端 `npm run build` 与后端 `mvn package` 已分别实测通过。

### 使用 MySQL（可选）

1. 本机 MySQL 8，账号 root/root（或修改 `application.yml` 中 `mysql` profile 的用户名密码）；
   连接串带 `createDatabaseIfNotExist=true`，库 `court_mediation` 会自动创建，表由 JPA 自动建立。
2. 以 mysql profile 启动：

```bash
cd backend
mvn spring-boot:run -Dspring-boot.run.profiles=mysql
# 或 jar 方式：java -jar target/mediation-platform.jar --spring.profiles.active=mysql
```

## 业务功能与对应操作

1. **申请登记**：「新建调解申请」记录五类案由（民间借贷/物业费/交通事故/邻里/小额买卖）、诉求金额、被申请人联系方式、证据清单、是否愿意线上调解、紧急程度、外地当事人标识。
2. **窗口分流**：案件详情 →「分流与排期」，核验材料（缺件可先行调解并登记补正）、确定线上/线下（外地当事人自动提示线上）、从名册指派调解员。
3. **智能排期**：选择时间段后系统按「案由专长匹配 + 在办量 + 时间冲突」综合打分推荐调解员；排期自动检测调解员时段冲突；每次**改期保留原记录**、累计改期次数，≥2 次触发红黄预警。
4. **调解过程**：逐次记录争议焦点、双方让步、协商过程与结果；支持电子送达（短信/邮件/站内，无有效号码自动失败留痕）、失联登记/恢复、证据补正。
5. **被申请人失联处置（重点）**：案件详情「失联处置」页全流程闭环——
   - 调解员多次联系失败时，**逐条登记电话、短信、地址核验、送达尝试**，记录当时使用的号码/地址与具体结果（无人接听、停机空号、短信未回、查无此人、拒收、送达失败等），**每次尝试都写入案件时间线**；
   - 累计联系失败达到**阈值（3 次）**，平台自动标记被申请人失联，并在案件页红色预警、同时向立案窗口推送「请核验送达地址」待办；
   - **窗口人员可直接查看全部联系尝试**，并可：① 补充被申请人新电话/新地址（后续联系与送达自动使用新信息）；② 核验送达地址（核验后预警消除）；③ 改为线下送达；④ 建议转立案；以上处置全部留痕进时间线；
   - **若转立案，前期全部电话/短信/地址核验/送达尝试证据自动汇编进材料包，并逐次标明第几次、何种方式、什么结果**，窗口接收即可见；连续过程材料卷导出同样包含该专节。
   - 被申请人重新联系上（登记「已联系上/已送达」）后失败计数归零、预警清除。
6. **协议与签署**：起草协议（一次性/分期、付款计划、担保人、履行期限、是否申请司法确认，自动生成规范文本）→ 模拟人脸核验（任意非 `0000` 的证件后四位通过，`0000` 演示不通过）→ 双方线上电子签名，签后协议生效。
7. **履行跟踪**：按协议生成一期或多期付款节点；执行联络确认到账，支持**部分履行**；定时任务每日扫描到期未付节点自动置逾期并预警（页面也提供「立即扫描逾期」按钮用于演示）。
8. **回访**：执行联络/法官助理登记电话/线上/上门回访与结果。
9. **司法确认**：申请后案件进入审查中，可下载《司法确认申请书》，法官助理审查通过后转入履行跟踪。
10. **转立案**：选择失联/证据争议/拒绝调解/协议逾期等原因，系统**自动汇编**申请、分流意见、历次排期改期、笔录、协议签署、履行、回访、送达、失联说明为材料包，窗口一次接收并登记诉讼案号，当事人无需重复补交。
11. **连续过程材料卷**：案件详情页「导出连续过程材料卷」随时把全过程时间线汇编成文本下载，供法官查阅。
12. **批量导入**：「批量导入」页支持 CSV 文件上传或粘贴，自带模板，逐行返回成功编号与失败原因。
13. **统计看板**：调解效率（成功率、在办、待分流）、案由分布、状态分布、协议履行到位率/已付总额/逾期节点、转立案原因分布、多次改期/失联/缺件风险统计（ECharts 图表）。
14. **角色工作台**：登录后首页按角色生成待办（窗口待分流/材料待接收、调解员待排期待调解失联联系、当事人出席确认/逾期告知、法官助理司法确认与转立案审核、执行联络分期与逾期回访）。

## 验证方式与验证结论

### 已实际执行的验证（本轮失联处置功能）

1. **后端编译打包**：`mvn package -DskipTests` 成功，产出 `backend/target/mediation-platform.jar`（约 50MB，含前端静态资源）。
2. **前端构建**：`npm run build` 成功，失联处置面板产物输出到后端 static。
3. **失联处置端到端接口回归**：`python3 scripts/e2e_missing.py` 对运行中的 jar 执行 **50 项断言全部通过**，覆盖：
   - 多角色登录与无令牌 401 拦截；
   - 调解员登记电话/短信/地址核验/送达尝试（轮次、方式、所用号码/地址、结果、说明落表），每次尝试均写入案件时间线并标明方式与结果；
   - 失败计数累计：1/2 次不预警、第 3 次达阈值后**自动标记失联 + 产生窗口核验送达地址预警**；非法方式/结果入参被拒；
   - 窗口待办出现「失联达阈值，请核验送达地址」；
   - 窗口四项处置：补充联系方式（案件电话/地址更新、空补充被拒）、核验送达地址（预警消除）、改为线下送达、建议转立案，均留痕；
   - **失联转立案材料包自动汇编前期全部联系证据，逐次标明第几次/方式/结果（无人接听、停机空号、地址不详），含窗口补充的新号码与核验/线下送达/建议处置**；窗口接收并回写诉讼案号；
   - 「导出连续过程材料卷」含失联联系过程专节及每次结果；
   - 登记「已联系上」后失败计数归零、不产生预警；种子失联案件（3 次尝试）与看板失联 KPI 正常。
4. **既有功能冒烟回归**：`python3 scripts/e2e_smoke.py` 对运行中的 jar 执行 **11 项断言全部通过**——新建申请→窗口分流→智能推荐调解员→排期→调解笔录→电子送达→手工失联登记→恢复联系（标记清除、失败计数归零）→连续过程材料卷导出。
5. 启动后种子数据经 `/api/dashboard` 核对：12 件案件、逾期/失联/缺件/多次改期风险与各角色待办均有数据；失联演示案件自带 3 次联系尝试与窗口处置全过程。

## 说明与边界（演示环境）

- 人脸核验、电子送达、电子签名为**业务流程级模拟实现**（返回确定性模拟结果并完整留痕），接入真实能力时替换 `MediationService.faceVerify`、`DeliveryService.send` 即可，表结构已预留核验得分/证件后四位/送达签收字段。
- 令牌存于内存，服务重启需重新登录；H2 为内存库，重启后数据由种子程序重新初始化。
- 金额单位均为人民币元；时间为服务器本地时间。
